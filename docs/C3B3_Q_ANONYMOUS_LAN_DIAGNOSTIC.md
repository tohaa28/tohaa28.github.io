\`vision-local-table-diagnostic (2).json\`, \`schema: printcheck.vision.local-order-dom-diagnostic.v1\`, время съёмки 2026-11-17T09:47:42.626Z.

**Никакие номера заказов, URL вложений, HTML страницы, персональные данные и оригиналы файлов не публиковались в GitHub.** В репозитории хранятся только агрегированные факты и синтетический браузерный тест, построенный *по числам*, без копирования реального содержимого.

**Вывод:** у каждой из 61 строк есть явно распознанная ссылка на карточку заказа. Прямых ссылок на макеты того же origin в таблице нет. Оставшиеся семь ссылок распознаны только *эвристикой названия файла/текста* и находятся вне origin либо небезопасны. Нельзя считать их подтверждёнными клиентскими макетами и автоматически загружать. Переход в карточку заказа и получение именно клиентских вложений через \`makets_popup\` остаются приоритетным маршрутом.

**Важно:** документ получен из уже открытого Vision overlay, который добавляет по одной дополнительной \`td\` с кнопкой к каждой исходной строке таблицы. Поэтому \`cell_count=488\` может включать 61 диагностическую ячейку Vision, а \`action_button_count\` может включать кнопки Vision. Число 488 **не является доказательством** восьми исходных колонок таблицы. Синтетический тест моделирует семь оригинальных ячеек + одну ячейку Vision = 488. Это проверяемая гипотеза, не факт о исходной верстке.

Файл не содержит HTTP-ответов карточек, списка вложений, имени макета, размера, реальной геометрии, Pantone/CMYK/spot, техтребований, экспертных ROI или меток брака. **По этому JSON нельзя признать тестовые макеты пригодными для обучения.**

## Решение по алгоритму

1. \`vision/orders/order-page-discovery.mjs\` остаётся единственным приоритетным маршрутом: авторизованная карточка \`/private/order/\` → внутренний \`data-orderid\` → \`/ajax/gifts/order?action=makets_popup&oid=...\` → клиентские \`a[data-maket]\` на \`/cart/act/mda\`. Конструкторы \`/drawing?action=getOrderItemPdf\` хранятся как эталоны, а не входные примеры модели.
2. Никаких запросов на семь подозрительных cross-origin links из таблицы. Они не должны ухудшать итог по валидной карточке заказа.
3. Поскольку 61 строка может означать 122 и более внутренних GET-запросов до скачивания макетов, пакетная проверка выполняется **по 10 заказов на один явный клик**, последовательно. Первую проверку рекомендуется проводить кнопкой одной строки.
4. Лимит исходных файлов **32 за один разрешённый пакет загрузок**, затем кнопка **«Новый лимит файлов»**. Прогресс, экспертные метки и уже обработанные вложения сохраняются в памяти открытой страницы. При исчерпании лимита посередине одного заказа сохраняется позиция файла; при продолжении не выполняются повторные GET ни карточки, ни ранее скачанного макета. Перезапуск/перезагрузка страницы очищает только временное состояние UI, не изменяя заказы.
5. Тесты \`tests/printcheck-vision-61-order-browser.mjs\` строят **полностью синтетические** 61 строки, 179 ссылок таблицы, 211 ссылок страницы, 7 запрещённых ссылок и 488 ячеек после overlay. Они проверяют маршрутизацию, отсутствие внешних запросов, последовательную проверку и корректное возобновление двухфайлового заказа на границе 32 загрузок.

## Следующий вход для реальной валидации

Запустить обновлённую закладку внутри тестовой LAN, нажать **«Проверить строку»** у одного заказа, затем скачать **«Отчёт JSON»** (анонимный, без исходных макетов). По реальному статусу строки будет видно, отсутствует ли внутренний ID, заблокирован ли popup, вернулась ли страница авторизации, найдены ли клиентские файлы, работает ли их физическое скачивание. Для исследования пригодности к обучению нужен отдельно собранный **локальный ZIP из явно размеченных тестовых заказов** на пользовательском \`D:\VisionCheckLab\` и независимая ручная ROI-разметка.
