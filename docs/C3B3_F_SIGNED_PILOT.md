# PrintCheck Vision — C3B.3.F: закрытый пилот с проверяемым происхождением

Дата: 2026-11-17. **Реальная экспертная выборка не подтверждена, производственная проверка не активирована.** Этот цикл поставляет код для будущего закрытого испытания и проводит сквозные синтетические тесты.

## Цель

Получить не просто JSON с пометкой verified, а проверяемую последовательность:

**исходные байты заказа/изображения/векторного макета → одинаковое слепое задание → два независимых ответа → разбор конфликтов → внешний аудитор → криптографически подписанный отчёт → отдельно сохранённые региональные результаты каждого алгоритма → агрегированные TP/FP/FN/TN.**

Каждый этап должен быть связан SHA-256 исходных байтов. Если что-то отсутствует, изменилось, противоречит исходнику или не подписано доверенным аудитором, данные не становятся эталоном.

## 1. Что реализовано

- vision/dataset/prepare-pilot-signoff.mjs — подготовка **неподписанного** манифеста. Все четыре проверки (достоверность двух экспертов, оригинал источника, физическая калибровка, план отбора областей) заранее выставлены в false. У конфликтных областей нет автоматического решения; они остаются manual. Черновик не может пройти проверку до отдельного решения.
- vision/dataset/pilot-attestation.mjs — проверка Ed25519 подписи по заранее доверенному SPKI SHA-256 ключа (trust pin), байтов исходного изображения/векторного файла, трёх приватных доказательных файлов, SHA неизменяемого задания, двух отдельных ответов и самих результатов исследований. Подпись должна покрывать **точные байты JSON** манифеста, не абстрактный JS объект.
- Результаты каждого исследовательского метода возвращаются **отдельно**: нельзя объединить параллельные границы с normal ray как две метки одной области или перезаписать одно исследование другим. Оставшиеся спорные/manual области исключаются, а не считаются хорошими.
- exportPilotEvaluations() — запись исследовательских JSON только в существующий приватный каталог. На POSIX проверяет 0700 у каталога и создаёт файлы 0600 без перезаписи. Если хотя бы один обязательный вход не подтверждён, файлы не создаются.
- tests/printcheck-vision-pilot-attestation.test.mjs — подписи с временными тестовыми ключами, подмена оригиналов, ревизий, ключа, оценки, дубли/пропуски областей, корректная обработка abstention, а также приватность вывода.
- tests/printcheck-vision-pilot-python-e2e.mjs — полный сквозной **синтетический** прогон с двумя ответами, подписанным отчётом, созданием приватных JSON по двум методам и фактическим запуском существующего Python оценщика.

## 2. Какие доказательства обязательны

Все файлы хранятся **только в закрытом локальном каталоге** и должны быть получены разрешённым способом.

| Файл | Что доказывает или фиксирует |
|---|---|
| task.json | Одинаковые координаты и SHA-256 изображения для обоих специалистов |
| image.png | Точные байты файла, который видели эксперты |
| artwork.svg / artwork.pdf | Оригинал макета, не предпросмотр |
| source-evidence.bin | Снимок источника заказа, артикула, конструктора, поля и технологии |
| calibration-evidence.bin | Данные о физическом размере, размещении, преобразованиях и фактической единице мм |
| sampling-evidence.bin | Зафиксированный до анализа план отбора областей, в том числе непредложенные алгоритмом контрольные зоны |
| expert-a.json / expert-b.json | Независимые ответы рецензентов без подсказок детектора |
| comparison.json | Результаты двух и более алгоритмов на одной и той же разметке |
| attestation.json | Проверенные аудитором выводы, SHA всех перечисленных файлов, метка train/validation/test, окончательное решение по каждой области |
| attestation.sig | Отдельная бинарная подпись Ed25519 по точным байтам attestation.json |
| auditor-public.pem | Только открытый ключ аудитора; его SHA-256 SPKI должен быть заранее подтверждён по другому защищённому каналу |

Значение digest одного лишь доказательного файла не доказывает его истинности. Код проверяет **целостность и соответствие подписи**, а аудитору остаётся проверить фактическую подлинность заказа, физический масштаб, технологию и полномочия экспертов.

## 3. Сквозной запуск в закрытой среде

Ни один из следующих файлов **не загружать в публичный GitHub, комментарии PR или чат**.

### Подготовка черновика

Уже после получения двух независимых локальных ответов:

    node vision/dataset/prepare-pilot-signoff.mjs task.json image.png artwork.svg source-evidence.bin calibration-evidence.bin sampling-evidence.bin expert-a.json expert-b.json comparison.json attestation-draft.json

Черновик содержит утверждения false, незаполненный adjudicator_ref_sha256 и доказательства решений регионов null. Это специально сделано, чтобы подпись по нерассмотренному черновику не считалась приёмкой.

Аудитор независимо проверяет каждую форму, согласованные нормативы, происхождение двух ответов, что эксперты не видели предсказаний, точность матрицы и доказательность отбора. Он исправляет только конфликтные решения, задаёт fingerprint собственной компетенции, связывает каждый регион с реальным файлом доказательств и **лишь после этого** отмечает четыре подтверждения true. Окончательный JSON подписывается отдельным Ed25519 ключом.

### Пара ключей аудитора (пример для OpenSSL 3)

На локальной доверенной машине аудитора; приватный ключ не хранить в рабочем каталоге репозитория:

    openssl genpkey -algorithm Ed25519 -out auditor-private.pem
    openssl pkey -in auditor-private.pem -pubout -out auditor-public.pem

На POSIX установить права приватного ключа 0600. На Windows ограничить ACL через штатное управление правами файла. Не вставлять личный ключ в командную строку, чат, историю Git или журнал. Не генерировать ключ прямо внутри публичного CI.

SHA-256 DER SPKI открытого ключа:

    node -e "const fs=require('fs'),c=require('crypto');const k=c.createPublicKey(fs.readFileSync('auditor-public.pem'));console.log(c.createHash('sha256').update(k.export({type:'spki',format:'der'})).digest('hex'))"

Отпечаток следует независимо закрепить в приватном регламенте до получения данных. Не доверять fingerprint, присланному в одной папке с потенциально подменённой подписью: иначе злоумышленник заменит и ключ, и подпись.

### Подпись окончательного отчёта

    openssl pkeyutl -sign -rawin -inkey auditor-private.pem -in attestation.json -out attestation.sig

Менять пробелы или форматирование attestation.json **после** подписи нельзя. Подпись хранить как бинарный файл длиной 64 байта.

### Проверка и локальные результаты

Создать защищённый каталог пилота. На POSIX: mkdir -m 700 private-research-output. Затем:

    node vision/dataset/pilot-attestation.mjs task.json image.png artwork.svg source-evidence.bin calibration-evidence.bin sampling-evidence.bin expert-a.json expert-b.json comparison.json attestation.json attestation.sig auditor-public.pem SPKI_SHA256 private-research-output

Команда проверяет все файлы и подпись, затем выдаёт отдельно:
- private-research-output/vision-research-parallel.json
- private-research-output/vision-research-normal.json

В каждом файле только один исследовательский алгоритм. Имена конкретных методик должны совпадать с их идентификаторами в comparison.json.

Обезличенные статистические отчёты по отдельным методам:

    python vision/dataset/evaluate.py private-research-output/vision-research-parallel.json --split test
    python vision/dataset/evaluate.py private-research-output/vision-research-normal.json --split test

Данные становятся **региональными исследовательскими метками с утверждением аудитора**, а не полным технологическим допуском макета. Сам evaluate.py не повторяет криптографическую проверку: проводить его только над уже проверенным локальным результатом данного модуля. По меньшим или неоднозначным группам метрики могут отсутствовать или быть статистически нерепрезентативны.

## 4. Как выбрать реальную контрольную выборку

Стартовать только после разрешения на внутреннее использование пользовательских макетов:

1. Сначала определить варианты технологии (шелкография, DTF, УФ, деколь и т.д.) и по каждому зафиксировать численные требования с исходными документами и датой.
2. Сформировать набор по исходным **семьям заказов/логотипов**, не по отдельным PDF-страницам. Проверить визуально почти одинаковые логотипы (изменённый размер, поворот, фон, другое имя файла), включить их в одну family.
3. Зарезервировать закрытый test-holdout до настройки детекторов. Оптимизировать параметры только на train/validation. Сам test не используется для подбора thresholds.
4. До ознакомления экспертов с результатами поиска зафиксировать две страты: потенциально дефектные участки и контрольные области, не предложенные алгоритмом. Иначе среди «нормальных» мест не появятся настоящие false negatives.
5. Задание обоим рецензентам должно быть идентичным и слепым; при конфликте требуется отдельное обоснование и третья независимая экспертиза либо статус manual.
6. На итоговом наборе отдельно считать TP/FP/FN/TN, покрытие (сколько manual), распределение по технологии, многообъектным/растровым/векторным исходникам и погрешность мм. Не публиковать значения по небольшим группам, не раскрывать исходные ID.
7. Ни скриншоты ошибок предыдущего PrintCheck, ни PDF отчёты с машинными прогнозами не являются ground truth без экспертного подтверждения.

## 5. Блокеры промышленной готовности

- В этом цикле **нет фактически подписанных реальных заказов** или независимо подтверждённых пар экспертных отзывов. Поэтому real-data precision/recall нельзя заявлять.
- SHA-256, Ed25519 и внешний доверенный ключ подтверждают связь файлов и ответственность аудитора, но не истинность измерений без проверки доказательств человеком.
- Режим compare-region-methods измеряет кандидатов в ROI. «None» не означает технологическую годность всей формы.
- Правильность полного PDF painter, всех обводок, растровых компонентов, порядок наложения красок, и влияние материала основы всё ещё требуют отдельной геометрической проверки.
- При недостаточном размере проверки и отборе только подозрительных мест accuracy/recall будут смещены.
- Ни один экспериментальный вывод не меняет основную «Макетную» и не создаёт автоматическое production OK/ERROR.
