# Vision AI — обсуждения по артикулу и технологические замечания

**Этап M3.12 · 18.11.2026 · только экспериментальный testgifts.local**

## Зачем

Дизайнер при обнаружении дефекта может написать в обсуждение **конкретного
артикула заказа**, приложить текст, скриншот выделенного участка или ответить
после исправления. Такой материал ценнее имени PDF, потому что содержит
человеческую аргументацию, технологический контекст и иногда локализацию
дефекта. Но ни слова «ошибка», ни приложенного PNG недостаточно, чтобы
доказать конкретную нарушенную норму или выбрать неверный/верный PDF.

## Подтверждено исходным кодом

- Тестовая страница списков: `http://psk.testgifts.local/devorders`.
- Чтение карточки: только существующий авторизованный GET
  `/private/order/{номер}` на `psk.testgifts.local` или `testgifts.local`.
- Распознавание клиентских PDF из существующего read-only popup
  `/ajax/gifts/order?action=makets_popup&oid=...`.
- Доступный HTML карточки и popup пока **не подтверждает**, где именно
  AJAX-обработчик обсуждения, как связаны тексты со строкой/местом
  нанесения и как получить медиа без нового непроверенного запроса.

## Реализовано: этап 1 / структура без извлечения личных данных

`vision/orders/discussion-probe.mjs`:

- ищет элементы управления «Обсуждение», «Комментарии», «Переписка» и
  близкие варианты по открытой DOM-структуре карточки, включая иконки
  с атрибутами `class`, `aria-label`, `data-action`;
- считает связь элемента управления с `data-orderitemid`, `data-item-id`,
  `data-article` либо помечает связь как неизвестную;
- отмечает наличие **уже присутствующих в HTML** веток, сообщений и
  изображений (приблизительные структурные кандидаты);
- только по уже присутствующим текстам формирует **НЕПРОВЕРЕННЫЕ**
  классы тем: тонкие печатаемые элементы, пробелы/выворотки,
  границы поля, цвета, шрифты, разрешение, прозрачность/градиенты,
  совмещение с конструктором;
- не открывает модальные окна, не вызывает `onclick`, не скачивает
  изображения и не делает сетевых запросов.

`vision/orders/order-page-discovery.mjs`: отдельная операция
`inspectOrderDiscussionFromRow`. Она читает только разрешённую карточку
одним GET, удаляет из HTML потенциально загружаемые медиа-теги,
создаёт неактивный DOM и передаёт его в структурный анализатор.

`vision/orders/overlay-entry.mjs`: кнопки **«Найти обсуждения»** и
**«Обсуждения JSON»**. Первая последовательно читает карточки; вторая
скачивает на компьютер `vision-local-discussion-probe.json`.
Без запуска проверки PDF и без записи ответов обратно на сайт.

**Важно:** диагностический JSON содержит только индексы строк таблицы,
количества кандидатов, фиксированные классы и отказы. В него не
включаются номер заказа, номер артикула, HTML, сообщения, имена авторов,
путь/URL скриншота, сами скриншоты или cookie.

## Проверка на реальной локальной странице

1. Открыть авторизованный `http://psk.testgifts.local/devorders`.
2. Установить/обновить только тестовое расширение Vision (из
   изолированной директории предпросмотра).
3. Нажать **«Найти обсуждения»**, затем **«Обсуждения JSON»**.
4. Передать только скачанный обезличенный JSON для сопоставления
   реальных типов элементов (системные GET/POST для открытия обсуждений
   НЕ вызывать и коды запросов не угадывать).
5. При отсутствии обнаруженных веток нельзя делать вывод
   «нет комментариев»: обсуждение может загружаться только по кнопке.

## Следующий этап после реального HTML-подтверждения

Для разрешённого локального доступа в согласованной тестовой среде
необходимо установить точную *документированную read-only* схему
загрузки сообщений и вложений. Не использовать для этого
`Согласования макетов`, изменяющие запросы, POST, несанкционированные
маршруты или обход сессии.

Приватное хранилище исследования должно отдельно фиксировать:

- pseudonymous order family + конкретный article/item + выбранное
  нанесение и версия макета, к которой относится комментарий;
- исходный текст/скриншот **только в локальном защищённом архиве**
  после удаления персональных данных;
- автора по роли (дизайнер, заказчик и т. д.), дату и последовательность
  ответов, если эти поля подтверждены HTML/сервисом;
- классификацию: замечание о дефекте, вопрос, исправление, подтверждение
  после исправления, обсуждение стоимости/сроков, не связанное с макетом;
- пару «дефектное состояние / исправленное состояние», если обе
  действительно установлены;
- независимую ROI-разметку скриншота с трансформацией
  координат в исходный PDF и физический масштаб, если он подтверждён.

Возможное поведение модели: слабый текстовый тег → предложение ROI →
две независимые экспертные проверки → согласование → семейная
контрольная выборка. Без этой цепочки `training_ready=false`.
Не объявлять отсутствие сообщений доказательством «макет годен».

## Безопасность

Публичный GitHub содержит только код и **синтетические тесты**.
Чужие тексты, скриншоты, cookie, имена, частные HTML и URL в
репозиторий, Issues, логи Actions или внешнюю нейросеть не передаются.
Текущий статус: **разведка структуры, реального извлечения переписки
не подтверждено**, `production_approved=false`, `training_ready=false`.
