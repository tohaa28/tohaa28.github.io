## 3. Назначение Макетной
Макетная — веб-редактор макетов gifts.ru, запускаемый bookmarklet/launcher поверх авторизованной страницы gifts.ru.

Главный рабочий поток:
1. прочитать свежую корзину/заказы gifts.ru;
2. показать реальные заказы и позиции;
3. выбрать заказ;
4. выбрать артикул;
5. выбрать точное место нанесения;
6. найти связанный конструктор/шаблон из «Макеты для заказа» → «Шаблоны макетов»;
7. открыть шаблон и определить поля `[print1]`, `[print2]`, ...;
8. разместить логотип;
9. проверить через PrintCheck;
10. экспортировать PDF;
11. при наличии mapping передать данные в Редактор мокапов и сформировать PNG/ZIP.

Главный принцип: ничего не угадывать, если gifts.ru даёт явную связь/название/код.

## 4. Источники данных gifts.ru
Корзина:
- всегда перечитывается с gifts.ru при запуске/refresh;
- локальный кэш не является источником истины;
- карточка заказа кликабельна целиком;
- позиции одного заказа объединяются в одну карточку;
- реальные артикулы, тиражи, названия, нанесения и места берутся со страницы заказа.

Связь шаблона:
- не открывать «Согласование макетов»;
- использовать «Макеты для заказа»;
- вкладка «Шаблоны макетов» содержит авторитетную связь артикул ↔ конструктор;
- `[print1]` = первое поле, `[print2]` = второе и т.д.;
- места должны называться дословно как в заказе, вместе с кодами/цветовыми уточнениями;
- если данных нет, не придумывать «лицо», «оборот» или другой place.

Пример ранней контрольной логики: заказ 7920509, артикулы 15637, 17488 и др.; для позиций без drawtask/place нельзя фантазировать место.

## 5. Текущий UX заказов
Сохранённая согласованная логика:
- до выбора заказа список заказов занимает всю доступную ширину;
- после открытия заказа рабочая область появляется плавно;
- карточки заказов одной строки выравниваются по высоте самого высокого заказа;
- многопозиционный заказ в компактном виде всегда показывает первый настоящий артикул;
- остальные позиции раскрываются плавно;
- раскрытие происходит при hover;
- стрелка — только визуальный индикатор, не отдельная интерактивная кнопка;
- focusin/focusout обеспечивает клавиатурный аналог просмотра;
- одно-позиционный заказ не имеет стрелки;
- счётчик позиций был утверждён как 12.5 px / weight 750 в полноширинном представлении;
- бейдж мокапа не должен перекрывать тираж.

Шаг 1:
- одна общая рамка артикула;
- внутри: артикул, название, тираж, превью, нанесение, место;
- если артикул один — выбрать автоматически;
- текст параметров и подписей внутри шага 1 — 10 px, font-weight 400;
- внешняя зелёная рамка сохраняется;
- внутренняя зелёная рамка списка артикулов убрана;
- миниатюра 76×76;
- отдельный дублирующий блок под списком не нужен.

Шаг 2:
- появляется после выбора артикула;
- полные названия мест + коды;
- не подменять реальные имена.

Шаг 3:
- редактор;
- кнопки/инструменты: центр, fit, произвольный поворот, ±90°, crop to field, удалить/загрузить логотип;
- при выборе поля показывать размер поля;
- размер шаблона показывать только в режиме «Шаблон целиком»;
- при выборе артикула пользователь хотел сначала всегда открывать «Шаблон целиком»;
- для одностраничного шаблона пользователь хотел полностью скрывать навигационные подписи/кнопки страницы;
- «Добавить логотип в остальные поля» пользователь хотел перенести к инструментам добавления логотипа и убрать из левого фрейма.

Шаг 4:
- скачивание показывается только после добавления логотипа.

## 6. Поля шаблона
Основной алгоритм:
- synthetic fields не создавать;
- primary: реальные окрашенные поля;
- fallback: формы с fill opacity примерно 98%;
- исключать зелёную служебную область слева сверху;
- исключать таблицу заказа/техинформации;
- arbitrary/freeform — использовать реальный shape, не bbox;
- при просмотре свободной/наклонной формы можно горизонтально ориентировать её относительно длинной стороны только в режиме просмотра поля, не изменяя другие поля;
- размеры поля должны соответствовать физической геометрии шаблона;
- несколько полей поддерживают разные логотипы;
- итоговый PDF может содержать все заполненные поля.

## 7. Работа с логотипом
- растровые и векторные логотипы поддерживаются;
- исходные пропорции не растягивать;
- default fit — около 95% поля;
- crop to field должен обрезать корректно;
- загруженный логотип не должен получать фон, которого в исходнике нет;
- при возврате в корзину рабочее состояние правой панели очищается; ранее существовала логика сохранения незавершённого макета, но UI «Вернуться к открытому макету» пользователь позже попросил скрыть;
- при выходе в корзину выгружать logo canvas и PrintCheck overlays.

## 8. Редактор мокапов
Исторически модуль сначала разрабатывался отдельно, затем интегрирован.

Ключевые требования:
- данные приходят из Макетной автоматически;
- ручные «Взять данные Макетной» и «Импорт handoff JSON» скрыты;
- handoff через postMessage/bridge с fallback localStorage;
- передаются order/article/product/method/place/applicationId/printN/геометрия/фото/artwork;
- mapping хранится на GitHub;
- одно поле может иметь несколько фото;
- одно фото может иметь несколько полей;
- новый макет автоматически применяет сохранённую mapping;
- каждое mapped photo создаёт отдельный мокап;
- combined export: один PDF + N PNG;
- кнопку «Редактор мокапов» показывать по доступности выбранного артикула/поля; наличие artwork нужно для PNG, но не обязательно для входа/разметки;
- фон исходного логотипа не добавлять и не выдумывать.

Mapping actions:
- «Сохранить привязку»;
- «Сохранить изменения»;

## 11. PrintCheck
PrintCheck — отдельный модуль; UI-задачи заказов/мокапов не должны менять его алгоритм.

Последняя зафиксированная алгоритмическая линия:
`PrintCheck-coverage-swt-v25-multisegment-ink`.

Основные инварианты:
- проверять нанесение только внутри выбранного поля;
- шрифты в нанесении запрещены; в шаблоне/вне поля допустимы;
- градиенты, прозрачности, эффекты в нанесении запрещены;
- пунктирная рамка поля — не нанесение;
- positive/negative считаются внутри одной печатной краски;
- граница разных цветов не является small-element дефектом;
- угловое схождение букв само по себе допускается;
- повторяющиеся/протяжённые реальные тонкие зоны должны находиться;
- растровые и векторные лого приводятся к общей геометрической модели;
- ручной параметр маски убран, выбор автоматический;
- контрольная пользовательская метафора: круг минимально допустимого диаметра;
- кружки дефектов без центральной точки;
- safe area / охранное поле;
- разрешение raster;
- цветовая модель по виду нанесения;
- pending status: «поиск мелких элементов...» до завершения проверки;
- краткий отчёт не должен скрывать важные ошибки;
- алгоритм v25 не считать подтверждённым на исходном пользовательском LM1 только по unit tests — нужен реальный повторный прогон.

Подробности: `PRINTCHECK_HANDOFF_2026-10-08-v25.md`.
