## P0. Реальная проверка RGB/CMYK после подтверждённого исправления

### Факты
- Последняя опубликованная сборка **Макетная r7fa6f062**, PrintCheck **v25 rb14f6d50**, CI **39607112412 SUCCESS**, настоящий WASM VectorCraft **39606367485 SUCCESS**.
- Исправлена «лже-CMYK» смена режима (VectorCraft теперь вызывает native file.documentColorMode с convert=true), и ложные RGB сигналы PrintCheck от неиспользуемых операторов/ресурсов.
- Пользователь формулировал CMYK → RGB с жалобой, что PrintCheck видит RGB. Это ожидаемое поведение для такого перехода. Может иметься в виду RGB → CMYK; **не делать без уточнения неверные исправления**.
- Актуальная запись: [MAKETNAYA_VECTORCRAFT_COLOR_PDF_EVIDENCE_2026-10-21.md](MAKETNAYA_VECTORCRAFT_COLOR_PDF_EVIDENCE_2026-10-21.md).

### Минимальный сценарий пользователя
1. Перезагрузить Макетную через bookmarklet в **авторизованном gifts.ru**; проверить UI r7fa6f062 и PrintCheck v25 rb14f6d50, обновить кеш.
2. Выбрать заказ, конкретный артикул, код места, конструктор и физическое поле. Загрузить исходный **RGB логотип**, где реальные цветные объекты, не пустой RGB resource.
3. Открыть VectorCraft, изменить **режим документа RGB → CMYK c преобразованием объектов** (проверить какие именно действия пользователь выполняет). Вернуть в Макетную кнопкой «Перенести на шаблон артикула».
4. После завершения повторного PrintCheck снять сообщение о цветности, event gwb-printcheck-editor-return и объект gwbPrintCheckLastEditorReturn.originalColorModels. Сравнить исходный и вернувшийся PDF по реальным painted operators и задействованным XObject: RGB, CMYK, Gray, Pattern, ICC, spot.
5. Повторить обратный переход **CMYK → RGB** — при реальных RGB объектах PrintCheck обязан видеть RGB, если тип печати их запрещает.
6. Проверить PDF, содержащий CMYK вектор + RGB растр, PDF с RGB setColor без последующего paint, и PDF с неиспользованным Image XObject; первые должны учитывать реальные раскрашенные элементы, последние — не давать ложную ошибку.
7. Проверить, что исправленный логотип заменяет только текущее поле, преобразование не меняет размер, offset, clips, текст и слой изображений, а «поиск мелких элементов…» запускается заново. Не менять original CMYK/RGB автоматически при импортировании файла в Макетную.

### Если остаётся дефект
- Получить (от пользователя) редактируемый небольшой тестовый PDF, без персональных заказов. Исследовать **реальный** PDF из экспорта, а не только метаданные или RGB превью.
- Добавить test-first case в tests/vectorcraft-runtime-browser.mjs, tests/logo-preflight-browser.mjs, tests/logo-preflight.test.mjs.
- Источники: tools/vectorcraft-bridge.rs, assets/logo-preflight.mjs, assets/logo-color.mjs, assets/cmyk-roundtrip.js, tools/patch-logo-editor-bridge.mjs.
- Не исправлять проблему путём удаления RGB-ошибок PrintCheck или объявления CMYK по document.color_mode.
- Если виноваты ICC conversion или объектные профили, явно документировать ограничения и проверять вход/выход CMS.

## P1. Печатные требования PrintCheck

- Проверить на реальных проблемных логотипах тонкие линии, островки, перемычки, позитив/выворотку, подавление ложных стыков и пересечений разных цветов.
- Растровые и векторные файлы должны приводить к согласованным физическим результатам; оценивать контур в масштабе мм и реальные dpi, не только предпросмотр.
- Проверить разные методы нанесения из серверного method-settings.json: модель/число красок, белую подложку, max colors, запрет raster при названных печатных красках.
- Ошибки исправления и последующего экспорта должны оставлять и старый логотип, и PDF заказа в прежнем состоянии.

## P1. Серверная пользовательская PDF-библиотека

- Старое требование: персональные PDF-макеты сохранять на сервере по аутентифицированному подарочному пользователю и артикулу. Есть прототип, но нельзя выдавать IndexedDB за доверенный сервер.
- Не публиковать приватные PDF/логотипы в GitHub, не включать их в общий handoff-архив, не хранить токены пользователя в HTML/JS source.
- Для доступа к аккаунту нужен проверяемый backend, авторизация на сервере и ограничения прав конкретного владельца.

## P1. TraceDraw / VectorCraft QA

- SVG/PDF, растр JPG/WebP/PNG, ICC, native CMYK и RGB, spot, многостраничность, rotation, перьевые кривые, границы объекта.
- TraceDraw исходный upstream не обеспечивает заявленный полный CDR roundtrip. Считать это отдельной задачей, не вписывать CDR как готовый вход.
- Проверить в embedded редакторе запреты лишних New/Open/Close и предел редактирования только текущего поля. Сложные SVG masks/clips/fonts/filters должны не исчезать молча.
- Векторный и растровый компоненты обязаны оставаться в фактическом PDF; трассировка должна сохранить реальные цвета по объектам.

## P2. Макеты gifts.ru и мокапы

- При замене PDF в заказе подтверждать оба этапа upload + verification + delete; если удаление не завершилось, оба файла остаются с предупреждением.
- Реальные авторизованные операции gifts.ru НЕ выполнять в автоматических тестах с клиентскими заказами.
- Редактор мокапов: цилиндры с развёрткой, реальный изгиб/перспектива, скрытие обратной стороны, связи фото ↔ поле, несколько фото на один артикул, сохранение общих настроек без фона.

## Обязательная последовательность любой новой реализации

1. Прочитать актуальный START_HERE и source STATE.
2. Пересчитать source/main SHA, сравнить каждый с checkpoint; проверить source/production SHA пользовательских JSON.
3. Создать новые backup branches обеих веток, перед началом работы.
4. Ограничить изменение указанными файлами; не переписывать весь minified bundle и не заменять целиком историю.
5. Добавить воспроизводимую регрессию. Проверить native Rust/WASM при изменении мостов.
6. Опубликовать через GitHub Actions; дождаться precheck → publish → browser_verify SUCCESS, затем отдельно live engine check при необходимости.
7. Сверить опубликованный HTML и версию, исходный/production SHA JSON, создание новых checkpoints source/main; обновить handoff.
