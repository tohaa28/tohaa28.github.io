Продолжать текущий веб-редактор без перезапуска проекта и без отката ранее работающего функционала. Любые новые правки интерфейса должны быть локальными и не должны ломать загрузку заказов, получение шаблонов, выбор артикула/места нанесения, работу редактора, добавление логотипов, сохранение/скачивание макета и существующую логику авторизации gifts.ru.

## 2. Назначение веб-редактора
Редактор должен брать данные существующего заказа gifts.ru и позволять техническому дизайнеру быстро подготовить макет по выбранным артикулам и местам нанесения.

Основной пользовательский поток:
1. Получить заказ по номеру / показать доступные заказы из корзины.
2. Прочитать состав заказа, артикулы, выбранные виды и места нанесения.
3. Получить шаблоны выбранных нанесений без запуска производственного задания и без открытия лишних рабочих панелей.
4. Выбрать артикул и нужное поле нанесения.
5. Добавить один или несколько логотипов в шаблон.
6. Разместить/масштабировать/повернуть логотипы в поле нанесения.
7. Проверить технические ограничения до сохранения.
8. Скачать готовый макет с сохранением качества исходников.

## 3. Критические ограничения работы с gifts.ru
- Живой заказ использовать read-only.
- Не открывать и не использовать «согласование макета».
- Не нажимать переключатели/контролы, которые могут изменить заказ или запустить производство.
- Для шаблонов использовать данные/связи из блока «Макеты для заказа» / «Шаблоны макетов».
- Связь `артикул → шаблон/конструктор` брать из подписей и структуры Gifts, а не угадывать по имени файла.
- Названия видов и мест нанесения транслировать именно так, как они указаны в заказе; не заменять их общими «лицо/оборот», если заказ содержит более точные названия.
- Получать данные заказа и ссылки напрямую, где возможно; браузер нужен прежде всего для авторизации.

## 4. Простой режим — текущая логика шагов
Подробный режим пока полностью скрыт.

### Шаг 1 — выбор артикула
- Показывать список артикулов заказа.
- Если артикул в заказе один — выбирать его автоматически.
- В строке/карточке выбора достаточно основных данных: номер артикула, название, тираж.
- Не дублировать параметры артикула в нескольких местах.
- Убрать текст «нажмите на нужный артикул».
- Выбор должен быть визуально очевидным; активный артикул выделяется.

### Новое обязательное требование к карточке артикула (2026-09-26)
В САМОМ СПИСКЕ ВЫБОРА АРТИКУЛОВ каждая выбранная/активная карточка должна содержать в одной общей рамке:
- номер артикула;
- название;
- тираж;
- превью изображения товара;
- вид нанесения;
- место нанесения.

Превью, нанесение и место нанесения НЕ должны отображаться отдельным блоком под списком артикулов. Они должны быть встроены внутрь карточки/рамки выбранного артикула в списке. Форматирование должно быть аккуратным и ровным.

### Шаг 2 — выбор места нанесения
- Показывать шаг 2 только после выбора артикула.
- Размещать данные выбранного нанесения логически внутри блока выбранного артикула, а не отдельной повторяющей карточкой ниже списка.
- Само место нанесения пользователь выбирает прямо на шаблоне.
- Подсказка «Выберите нужное место нанесения прямо на шаблоне» видна только в режиме «Шаблон целиком».
- Когда конкретное место нанесения открыто, эту подсказку скрывать.
- При возврате к полному шаблону подсказку можно снова показывать.

### Шаг 3 — редактор
- Шаг 3 должен быть явно подписан в области редактора.
- На холсте показывается шаблон.
- Пользователь может добавлять логотипы и работать с их размещением.
- Должны сохраняться существующие функции перемещения, масштабирования, вращения, центрирования/вписывания и работы с полем нанесения.
- Если у артикула несколько полей, пользователь может выбрать одно/несколько/все нужные поля и разместить логотипы в соответствующих полях.
- Несколько логотипов должны быть допустимы; итог — единый макет со всеми размещёнными логотипами.

### Шаг 4 — сохранение/скачивание
- Показывать шаг 4 только после того, как в шаблон добавлен хотя бы один логотип.
- Сохранять исходное качество.
- Перед сохранением выполнять доступную техническую проверку.
- Если есть ошибки, предупреждать пользователя; ранее обсуждалась возможность требовать явное подтверждение для скачивания заведомо неправильного макета.

## 5. Карточки и компоновка
- Левая колонка ранее была увеличена по ширине; не возвращать прежнюю узкую ширину.
- Список артикулов должен выглядеть как явный интерактивный выбор.
- Не повторять одни и те же данные артикула 2–3 раза.
- Фото товара должно находиться внутри блока информации об артикуле.
- Вид нанесения и место нанесения должны находиться в той же общей рамке, что и выбранный артикул и его фото.
- Не создавать отдельный повторяющий информационный блок под списком.

## 6. Превью товара
- Превью должно загружаться автоматически.
- В заказе/на Gifts искать изображения товара по данным заказа или карточке товара.
- Ранее использовалась логика поиска JPG/WEBP/PNG; имена превью могут начинаться с кода артикула (пример: `15637_7_200x200.jpg`).
- Фото общее для артикула, а не отдельное для каждого места нанесения.
- Если первая попытка получения картинки не сработала, не ломать остальную карточку и не выводить отдельную пустую панель.

## 7. Работа с шаблонами и местами нанесения
- Названия мест нанесения читать из страницы заказа и переносить без искажения.
- Выбор поля должен соответствовать заказу и связанному application-template.
- На шаблоне поле нанесения всегда выделено цветом — это важный сигнал для определения выбранного поля.
- Не путать служебные рамки/пунктир шаблона с самим нанесением.
- Частично отсутствующие элементы конструктора не считаются ошибкой, если реальное поле нанесения сохранено и однозначно определяется.

## 8. Логика редактора и форматы
Сохранить ранее реализованную/заявленную поддержку:
- шаблон PDF/SVG;
- нанесение PDF, AI, SVG, PNG, JPG;
- PDF/AI с PDF-совместимым содержимым — использовать поддерживаемый PDF-контент;
- не ухудшать растр;
- сохранять вектор там, где источник векторный;
- SVG преобразовывать в векторный PDF при экспорте;
- CDR/EPS не подменять фиктивной поддержкой, если прямого парсинга нет.

Базовые инструменты редактора, которые нельзя потерять:
- просмотр всей страницы / конкретного поля;
- выбор поля;
- сброс;
- перемещение нанесения;
- изменение размера;
- сохранение пропорций;
- «Вписать в поле»;
- «Центрировать»;
- отображение ширины/высоты;
- проверка охранного поля;
- минимальное разрешение растров;
- требования из шаблона/заказа;
- сохранение макета и исходников.

## 9. Общая архитектура PrintCheck, которую нельзя нарушать
Каноническая цепочка данных:
`item_id → выбранное нанесение → application-template → техтребования позиции → макет → конструктор → реальное поле → нанесение → проверки → визуальный результат`

Источники имеют разные роли:
- заказ определяет что выбрано: артикул, метод, место, тираж, параметры;
- application-template привязан к конкретному нанесению;
- полный конструктор задаёт геометрию изделия;
- макет пользователя содержит нанесение;
- связи нельзя восстанавливать только по догадкам из имён файлов.
