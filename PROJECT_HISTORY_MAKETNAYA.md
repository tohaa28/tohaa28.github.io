## 2. Назначение Макетной

Макетная — веб-редактор макетов для gifts.ru, запускаемый через bookmarklet поверх сайта gifts.ru.

Основной сценарий:
1. пользователь авторизован на gifts.ru;
2. Макетная считывает корзину/заказы;
3. пользователь выбирает заказ;
4. выбирает артикул;
5. выбирает точное место нанесения;
6. открывается соответствующий шаблон/конструктор;
7. пользователь загружает и размещает логотип;
8. PrintCheck проверяет макет по техническим требованиям выбранного нанесения;
9. пользователь скачивает готовый PDF и при наличии привязок — мокапы.

Ключевой принцип: данные заказа, артикулов, мест нанесения и шаблонов должны соответствовать gifts.ru, а не угадываться локально.

## 3. Интерфейс Макетной

### Шаг 1 — выбор артикула

Карточка артикула содержит в одной рамке:
- артикул;
- название;
- тираж;
- превью товара;
- нанесение;
- место нанесения.

Если артикул один — выбирается автоматически.

Заказы в корзине группируются рамкой по номеру заказа. Вся рамка заказа кликабельна.

При возврате из заказа к списку заказов:
- правая рабочая область полностью очищается;
- старый макет, overlay, PrintCheck и загруженный логотип должны выгружаться;
- правая область переходит в состояние ожидания выбора заказа.

Текст «Войдите в gifts.ru, затем выберите заказ из корзины.» показывается только если авторизация действительно отсутствует.

### Шаг 2 — выбор места нанесения

Появляется только после выбора артикула.

Названия мест должны быть точными, как в заказе gifts.ru, вместе с кодами/типом нанесения.

`[print1]` — первое поле, `[print2]` — второе и т. д.

### Шаг 3 — редактор

Редактор содержит:
- загрузить/заменить логотип;
- подогнать;
- центрировать;
- произвольный поворот;
- ±90°;
- обрезать по полю;
- удалить логотип;
- масштаб/вписать поле.

Логотип по умолчанию вписывается примерно на 95% поля.

Кнопка «Шаблон целиком» доступна из просмотра поля.

Несколько полей поддерживаются независимо: в разных полях могут быть разные логотипы, экспортируется один итоговый PDF.

### Шаг 4 — экспорт

Показывается только когда есть добавленный логотип.

При наличии сохранённых мокап-привязок можно скачать PDF и один или несколько PNG мокапов.

## 4. Определение полей в шаблоне

Приоритет:
1. явно окрашенные поля;
2. fallback — фигуры с заполнением около 98% opacity.

Не использовать synthetic field.

Исключить из поиска:
- зелёную служебную область в левом верхнем углу;
- таблицу с заказом/технической информацией.

Поле произвольной формы должно использовать реальную форму объекта, а не bounding box.

Связь артикул ↔ шаблон и место нанесения должна следовать данным gifts.ru.

## 5. Bookmarklet / launcher

Канонический build source: `tools/build-launcher.mjs`.

`launcher.js` генерируется, вручную его не править.

Стартовая анимация:
- две двери;
- длительность около 2 секунд;
- двери реально разъезжаются после double requestAnimationFrame;
- логотип «М» закреплён на левой двери и уезжает вместе с ней;
- зелёной полосы/шва по центру нет;
- повторный запуск закрывает интерфейс обратной анимацией;
- reduced-motion не должен пропускать эффект.

Embedded Mockup Editor использует rebasing путей модулей внутри `srcdoc`. Критическая логика в `tools/build-launcher.mjs`: относительные `./assets/` внутри embedded mockup должны преобразовываться в абсолютные URL GitHub Pages.

## 6. Редактор мокапов

Основной файл: `mockup.html`.

Редактор автоматически получает handoff из Макетной. Ручные:
- «Взять данные Макетной»;
- «Импорт handoff JSON»
скрыты, но fallback-обработчики сохранены.

Автоматический handoff:
- embedded редактор запрашивает `gifts-mockup-handoff-request`;
- parent отвечает текущими данными;
- есть fallback через localStorage;
- standalone также может загрузить localStorage.

Кнопка «Редактор мокапов» доступна, когда выбран артикул/шаблон с полями. Для входа в редактор наличие логотипа не обязательно. Для генерации PNG логотип обязателен.

### Привязки

Канонический реестр: `mockup-profiles.json`.

Правила:
- фото-first: смена поля сама по себе не должна переключать фото;
- привязка точная: photo ↔ field;
- одно поле может иметь несколько фотографий;
- одна фотография может иметь несколько полей;
- для каждого размеченного фото создаётся отдельный мокап;
- сохранённые пользователем профили нельзя перезаписывать/терять;
- перед любой записью реестра заново получить свежий `mockup-profiles.json`.

Есть действия:
- сохранить привязку;
- сохранить изменения;
- удалить привязку;
- состояние сохранения/изменения/удаления должно визуально подтверждаться.

Мелкие фотографии артикула не добавляются в список разметки: на них неудобно ставить геометрию.

## 9. PrintCheck — назначение

PrintCheck проверяет только логотип/нанесение внутри выбранного поля по требованиям выбранного метода печати.

Важный принцип: PrintCheck — отдельный модуль проверки. При работе над ним нельзя ломать или менять остальную Макетную, мокапы, handoff, экспорт, корзину и прочую функциональность, если пользователь явно не попросил.

Основные файлы:
- `assets/logo-preflight.mjs`;
- `assets/logo-detail-check.mjs`;
- `assets/logo-detail-worker.mjs`;
- `assets/logo-detail-engine.mjs`;
- `tools/patch-artwork-preflight.mjs`;
- `tests/logo-detail.test.mjs`;
- `tests/logo-detail-browser.mjs`;
- `tests/logo-preflight-browser.mjs`.

Compiled bundle `assets/index-BpU9kvz8.js` вручную не редактировать для PrintCheck. Изменения интеграции делать через patcher.

## 10. PrintCheck — общие проверки

Проверяются:
- выход логотипа за поле;
- safe area / охранное поле;
- шрифты внутри нанесения запрещены;
- шрифты вне нанесения и в конструкторе допустимы;
- градиенты запрещены;
- прозрачности/эффекты в нанесении запрещены;
- цветовая модель по виду печати;
- для лазерной гравировки требуется чёрно-белое изображение без полутонов;
- white/black CMYK разрешены в соответствующих общих правилах;
- разрешение растрового файла;
- мелкие positive элементы;
- negative пробелы;
- отдельные маленькие объекты.

Пунктирная рамка поля является частью шаблона и не считается нанесением.

## 11. PrintCheck — правила мелких элементов

Это критическая часть проекта.

Пользовательская модель проверки: технический дизайнер мысленно/физически рисует круг диаметром, равным минимально допустимому элементу, и накладывает его на линии, перемычки, объекты и пробелы. Если контрольный круг не помещается — место является кандидатом на дефект.

Печатаемый цвет может быть любым: синий, чёрный, красный и т. д. Фон/пробел также может иметь любой визуальный цвет; важны фазы «печать» и «не печать».

Обязательные правила:
- raster и vector должны проверяться по одной геометрической модели после подготовки масок;
- SVG/PDF могут дополнительно давать исходную палитру;
- PNG/JPG проверяются по пикселям;
- ручная настройка маски удалена;
- фон и маска определяются автоматически;
- разные печатные цвета не должны создавать defects на границе друг с другом;
- positive/negative измеряются только в рамках одного печатного цвета;
- пересечение двух разных цветов не считается мелким элементом;
- антиалиасинговая полоса между цветами не является отдельной краской;
- угловое схождение линий/букв само по себе допустимо;
- повторяющийся/протяжённый настоящий тонкий участок является дефектом;
- настоящий narrow bridge должен находиться;
- настоящий узкий negative gap должен находиться;
- открытый внешний фон около одного контура не является negative gap;
- маленький реально отдельный объект должен находиться;
- один визуально цельный разноцветный рисунок нельзя дробить на тысячи «отдельных объектов».

Кружки:
- центрировать в найденной проблемной зоне;
- без центральной точки;
- диаметр кружка соответствует минимально допустимому размеру;
- не ставить цепочки кружков по обычным внешним краям толстых объектов.

## 14. Тестирование PrintCheck

Нужно сохранять regression coverage как минимум на:
- thick element: никаких positive markers по обычному краю/торцам;
- true thin line;
- true narrow bridge;
- wedge/corner convergence — не дефект;
- true white/noprint gap;
- open outside background — не gap;
- colour boundary — не positive и не negative;
- antialias boundary — не отдельный цвет;
- real third source colour сохраняется как ink-layer;
- PNG parity;
- SVG parity;
- PDF path;
- automatic mask;
- transparent artwork;
- light/dark backgrounds;
- isolated object;
- multicolour connected artwork не дробится на isolated;
- worker/cache chain;
- UI без ручной mask/threshold настройки.

## Дополнение 2026-10-06 — PrintCheck v16 exact Euclidean opening

После v15 обнаружена конкретная причина двух регрессий первой попытки exact opening: после замены chamfer distance на Euclidean Distance Transform в dilation-части `circleOpening` сохранилось старое деление `/3`. В результате Euclidean-расстояние ошибочно масштабировалось как chamfer 3/4 и реконструкция контрольного круга получалась примерно втрое шире.

Исправлено:
- `circleOpening` теперь использует exact Euclidean Distance Transform и для поиска центров контрольного круга, и для восстановления covered-area без старого `/3`;
- final local thickness остаётся Euclidean;
- candidate-компоненты по-прежнему проходят фильтрацию углов/торцов, но `taperToOneBody` теперь оценивает профиль толщины вдоль медиальной оси;
- длинная равномерно тонкая ветвь, присоединённая к толстому объекту, больше не отбрасывается как taper;
- короткий клиновидный сход/угол по-прежнему не считается дефектом;
- исправлена JS-ошибка typed-array: `Int32Array.map(i => [distance,width])` заменён на `Array.from(...)`, иначе пары профиля превращались в нули.

Новые/сохранённые regressions:
- thick straight/rounded element > limit → positive = 0;
- thin straight element < limit → positive > 0;
- thick diagonal bridge → 0;
- thin diagonal bridge → найден;
- narrow neck → найден;
- wedge/corner convergence → 0;
- long uniform 0.3 mm spur при норме 0.5 mm → найден;
- negative open-background / true-gap / same-colour channel, colour boundary, antialias transition, isolated-object tests сохранены.

## Дополнение 2026-10-07 — PrintCheck v19: двухсторонняя медиальная ось и ускорение EDT

По пользовательскому скриншоту одноцветного синего растрового рисунка при LM1 обнаружен характерный дефект v18: сотни жёлтых/голубых маркеров располагались цепочками вдоль обычных границ рисунка, а минимальные размеры часто были около одного пикселя (~0,02 мм в показанном прогоне). Одновременно анализ заметно замедлился.

Корневая причина false positive:
- старый `medialAxis()` принимал пиксель за осевой, если distance transform уменьшался хотя бы с одной стороны;
- на ступенчатой/кривой растровой границе это позволяло обычному краевому пикселю с радиусом 1 px попасть в «ось» и получить ложную локальную толщину 1 px;
- для negative та же ошибка могла принимать пиксели у стенки широкого белого канала за центр узкого пробела.

Исправлено в `PrintCheck-control-circle-v19-two-sided-medial`:
- осевая точка принимается только если distance transform убывает до границы в двух противоположных направлениях;
- проверяются 8 ориентаций, включая промежуточные 2:1 / 1:2, чтобы сохранять диагональные тонкие перемычки;
- поиск оси ограничен только диапазоном толщин, релевантным текущему контрольному кругу;
- широкая щель между двумя стенками больше не получает маркеры на своих краях;
- растрированная толстая кривая не создаёт однопиксельные positive-маркеры;
- короткие taper/corner convergence по-прежнему исключаются: добавлен анализ профиля ширины missing-компонента по расстоянию от основной формы;

- теперь EDT до opened-области вычисляется лениво максимум один раз на слой и переиспользуется;

## Дополнение 2026-10-07 — PrintCheck v22: SWT + контрольный круг

Пользователь повторно проверил тот же синий одноцветный LM1-растр после v20. Результат оставался неприемлемым: сотни маркеров всё ещё шли по обычным контурам. По запросу пользователя выполнен внешний поиск более подходящих методов.

Исследованные методы:
- Stroke Width Transform (Epshtein, Ofek, Wexler, CVPR 2010): ширина штриха определяется лучом от одной границы к противоположной, причём нормали границ должны быть примерно противоположны; это локальный и быстрый способ измерять именно полосу/штрих.
- Binary morphological opening дисковым структурным элементом: физическая модель «контрольного кружка»; opening сохраняет только области, где диск заданного диаметра помещается, а top-hat difference выделяет части, куда он не помещается.
- Medial-axis/EDT оставлен только как вспомогательная геометрия; основным детектором больше не является.

Итоговый алгоритм v22:
1. Для positive строится SWT по маске конкретной краски:
   - луч идёт от одной внешней границы элемента к противоположной;
   - противоположная граница принимается только при почти противоположных нормалях (допуск ±30°);
   - границы разных цветов блокируют луч;
   - фон по обе стороны должен принадлежать одной фоновой компоненте, чтобы отверстия внутри массивного объекта не превращались в ложную толщину внешнего контура.
2. Одновременно выполняется Euclidean disk opening диаметром, равным минимально разрешённому positive.
3. Positive считается дефектом только если:
   - участок удалён control-circle opening;
   - SWT подтвердил две реальные противоположные границы;
   - измеренная ширина меньше порога;
   - topology filter не классифицировал участок как допустимый свободный клин / короткий end-cap / taper.
4. Для negative используется SWT по белой фазе:
   - луч должен встретить противоположные стенки той же краски;
   - внешний фон с одной стенкой не считается пробелом;
   - граница другой краски блокирует измерение.
5. Полностью отдельные маленькие объекты сначала маркируются как isolated, после чего исключаются из positive/negative анализа. Это устранило двойной подсчёт dense-grid объектов.

Почему это лучше предыдущих v18–v21:
- обычный внешний контур толстой линии не имеет второй противоположной стенки на допустимой ширине, поэтому не даёт marker;
- свободный клиновидный сход может локально иметь две стороны, но не проходит control-circle topology confirmation;
- настоящая равномерная тонкая линия/перемычка проходит оба критерия;
- узкий белый канал между стенками той же краски проходит negative SWT;
- open background рядом с одной стенкой не проходит;
- расчёт больше не зависит от хрупкого local-max/medial ridge критерия на ступенчатом raster edge.

- browser verify passed, включая SVG/PDF/raster, colour boundary, thick curve, thin bridge, open channel, isolated 400-grid, antialias, auto mask and UI regressions.
